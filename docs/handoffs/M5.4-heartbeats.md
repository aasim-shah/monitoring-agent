## Summary

Agents report in every 30 seconds. The dashboard API lists a product's fleet with a status derived from heartbeat age, and shows per-agent detail.

## Delivered

| Piece | Behavior |
|---|---|
| `POST /agent/v1/heartbeat` (`@AgentRoute()`) | Schema-validated `Heartbeat` → 202 `{ accepted, policyVersion }`. Sequence ≤ last seen → `accepted: false`, nothing stored (conditional update, so concurrent replays cannot regress it). `sentAt` off by more than 5 min → stored in `clock_skew_seconds`. Updates version and capabilities; appends `agent_heartbeats`. |
| `agentStatus()` (`status.ts`) | `revoked` wins; otherwise `degraded` after 90 s without a heartbeat (enrollment time counts before the first one), `stale` after 5 min |
| `GET /api/v1/products/:productId/agents` (`agent.view`) | Fleet: hostname, OS, arch, version, environment, status, stale, last heartbeat, clock skew, duplicate-machine-ID flag (same `machine_id` on more than one active agent in the org) |
| `GET /api/v1/agents/:id` (`agent.view`, tenant resource `agent`) | Summary plus capabilities, policy version, current certificate (expiry, fingerprint), last 20 heartbeats |
| Tenant guard | New resource `agent` resolved by `pcp_resolve_agent_org/product`; product scope enforced through `can()` |

OpenAPI: `AgentSummary`, `AgentDetail`, heartbeat response; spec §15.3 and WB-03 §7 list the product-scoped fleet route.

## Test-suite hardening done here

- Agent test helpers enroll from random IPs (the per-IP enroll limit is shared across test files through Redis).
- Rate-limit tests (auth and enroll) make up to 21 attempts, so 11 always land in one fixed window.
- CA chain test verifies a few seconds after the dev CA's start (verification at exactly `notBefore` fails).
- `@pcp/connector-runtime`: concurrent credential submissions are covered by a new test (16 passed).
