# M15 Reports and Schedules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin schedules a daily report for a product at 08:00 in their timezone. Every morning the platform:
1. builds a deterministic snapshot of the prior complete local day
2. adds an AI executive summary whose numbers and citations are validated, or "Narrative deferred"
3. stores the report as a versioned row
4. delivers it by email, Slack, and webhook, and shows it in the app

Missing sources are listed, never shown as zero.

**Architecture:**
- **`packages/reports`** holds the pure parts:
  - window math (Luxon)
  - the daily template
  - the snapshot builder, over an injected `ReportSources` interface
  - the narrative step, over an optional `ChatProvider`, validated with `validateAnswer`
  - message rendering
- **The worker** owns everything that runs:
  - a dispatcher loop calls `pcp_due_report_schedules(now)` (SECURITY DEFINER, `pcp_scheduler`) every 60 s
  - it enqueues `report-generate` with job ID `report-generate__<org>__<schedule>__<localDate>`
  - it advances `next_run_at`
  - `report-generate` creates the report and its deliveries exactly once per schedule per local date, then enqueues `report-deliver` jobs
  - `report-deliver` sends through the existing notification channels
- **The API** has schedule CRUD with a "next run at" preview, report history and view, and the "Run now" and "Regenerate" actions, which enqueue jobs. **The web** gets the Reports & Schedules page.

**Tech Stack:** Luxon 3, Prisma 6 and RLS, BullMQ, nodemailer through the existing notification channels, `@pcp/ai-orchestrator` (`ChatProvider`, `validateAnswer`), VictoriaMetrics instant queries, NestJS 11, Next.js 15, Playwright.

**Spec:**
- spec §12.4, §13.2, §13.3
- inital.md §13
- master plan M15.1–M15.3, D21, §3 ("Daily report: 08:00 in tenant timezone, covering the prior complete local day"), Review Focus #3
- `docs/workbooks/WB-15-reports-schedules.md`

**Deferred:**
- **Weekly and monthly templates** (WB-15 open item). The `report_templates` table waits for them; the daily template lives in code (`template = 'daily'`).
- **Owner notification after 3 consecutive email bounces.** SMTP acceptance is not a bounce signal; this needs Resend bounce webhooks.
- **Scheduled AI investigations with selected tools** (§12.4). Reports reuse the scheduler and the owner-access check; tool-driven scheduled investigations follow with M16 approvals.

## Global Constraints

- **Window (D21, §3):**
  - The window is the prior complete local day in the schedule's IANA timezone: `[startOf(localDate), startOf(localDate + 1 day))`, converted to UTC.
  - A day is 23, 24, or 25 h long.
  - All timestamps are stored as UTC `timestamptz`, and timezone math uses Luxon.
- **One report per schedule per local date (BR-15-04):**
  - Unique `(schedule_id, local_date, version)`.
  - A scheduled run is always version 1. A retry or restart finds the existing version 1 and only resumes its pending deliveries.
- **Regeneration (BR-15-06):** creates version n+1 for the same local date. Earlier versions are never changed.
- **Numbers and data:**
  - Numbers come from the snapshot only (BR-15-01).
  - The LLM receives the sanitized snapshot summary only: section values, no log lines, no URLs with query strings, no secrets (BR-15-02).
  - Every number and `[S#]` citation in the narrative must validate against the snapshot. On failure the generator retries once, then stores "Narrative deferred" (BR-15-03, UC-15-05).
  - A missing source has value `null` with a reason, and is listed under "Data coverage and missing sources". It is never shown as 0 (BR-15-05).
- **Scheduling:** goes through `pcp_scheduler` functions only (BR-15-07). The worker runs as `pcp_app` with `withTenant` for everything else.
- **Delivery:**
  - Goes through the organization's notification channels (email, Slack, signed webhook) plus optional direct email recipients (at most 10).
  - Retries follow master plan §3: 5 attempts with exponential backoff, then dead. Every attempt's outcome is recorded in `report_deliveries`.
  - In-app delivery is the report itself in history.
- **Late runs:** a run that starts more than 15 min after `next_run_at` is still generated for the same window, and is marked `late = true` (WB-15 §9).
- **Owner access:** a schedule whose creator can no longer access the product fails with `not_found` and does not run (M15.1 test).
- **Permissions:**

  | Action | Permission |
  |---|---|
  | View reports and schedules | `report.view` |
  | Create, edit, delete, run, regenerate | `report.manage` |

  Everything is product-scoped and tenant-checked through `TenantScope` resolvers.

## Review Focus

1. **A schedule at 08:00 Europe/Berlin across DST.** Expected:
   - the 2026-10-26 run fires at 07:00Z and covers `[2026-10-24T22:00Z, 2026-10-25T23:00Z)` (25 h)
   - the 2027-03-29 run covers `[2027-03-27T23:00Z, 2027-03-28T22:00Z)` (23 h)
   - Asia/Karachi runs at 03:00Z over 24 h

   Task 2 (TC-15-01/02).
2. **The worker dies after generation but before delivery, then restarts.** Expected: still one `generated_reports` row, and each delivery is sent once. Task 3 (TC-15-03).
3. **The AI provider throws, or writes a number not in the snapshot.** Expected: the report is still stored and delivered, with "Narrative deferred" and the validation problems recorded. Tasks 2 and 3 (TC-15-04/05).
4. **A schedule for another tenant's product, or a report ID from another organization.** Expected: 404. Also, a schedule whose owner lost product access does not run. Tasks 3 and 4.
5. **A local time that does not exist (02:30 on a spring-forward day), or a changed timezone.** Expected: the run shifts forward by the DST gap (02:30 becomes 03:30 local, as Luxon does). After a timezone change, `next_run_at` is recomputed, and no second report is made for a local date that already has one. Tasks 2 and 4.

### Task 2: `packages/reports`: window, template, snapshot, narrative, render

**Files:**
- Create: `packages/reports/{package.json,tsconfig.json,vitest.config.ts}`

**Interfaces:**
- **Window:**
  - `reportWindow(timezone: string, localTime: string, runAt: Date) → { localDate: string; start: Date; end: Date; hours: number }`: the local date before `runAt`'s local date.
  - `nextRunAt(timezone: string, localTime: string, after: Date) → Date`: the first instant strictly after `after` whose local wall time is `localTime`. A non-existent local time moves forward to the next valid instant.
  - `isValidTimezone(tz: string) → boolean`
- **Template:** `DAILY_SECTIONS`, an ordered list of 12 entries `{ key, title, id }`. The IDs are `S1`…`S12`, in the order of inital.md §13: executive summary, product health, infrastructure, application, user analytics, database health, advertising, deployments, security and availability, anomalies, suggested actions, coverage.
- **Snapshot:**
  - `interface ReportSources`, with every method taking `(window)`:
    - `incidents()` → `{ opened, resolved, openNow, bySeverity }`
    - `hosts()` → `Array<{ hostname, cpuAvg, cpuMax, memoryAvg, diskMax }> | null`
    - `logErrors()` → `{ errors, warnings } | null`
    - `databases()` → `Array<{ name, provider, status, ok }> | null`
    - `websites()` → `Array<{ url, uptimePercent, tlsDays }> | null`
    - `previous`: the same shape for the prior window, used for comparisons
    - `coverage()` → `Array<{ source, status: 'ok' | 'partial' | 'missing', reason? }>`
  - `buildSnapshot(sources, window) → Promise<Snapshot>`
  - `Snapshot = { window, sections: Array<{ id, key, title, status: 'ok' | 'missing', data: unknown, reason?: string }>, anomalies, actions, coverage }`
  - Always-missing sections, until their sources exist:
    - user analytics: "Google Analytics not connected (M13b)"
    - advertising: "No ad platform connected"
    - deployments: "No deployment source connected (GitHub, M7)"
    - application performance, when no log metrics exist
  - Anomalies: the change against the previous window when `|Δ| ≥ 50 %` and the current value is ≥ 10 (counts) or ≥ 20 (percent).
  - Actions: deterministic rules, for example "disk ≥ 85 % on X: free space or grow the volume", "website uptime < 99 %", "open critical incidents".
- **Narrative:**
  - `narrate(snapshot, provider: ChatProvider | null, opts: { disabled: boolean }) → Promise<{ text: string | null; status: 'verified' | 'deferred' | 'disabled'; problems: string[] }>`
  - The prompt holds `summarize(snapshot)` only (the section `id`, title, and data JSON) and asks for 3–6 sentences citing `[S#]`.
  - It validates with `validateAnswer(text, sections.map(s => ({ id: s.id, json })), '')`, retries once, then returns `deferred`.
  - `[S#]` citations count as evidence IDs: the call passes `S`-prefixed IDs, and `validateAnswer` gains a citation pattern option.
- **Render:** `renderReport(report: { snapshot, narrative, narrativeStatus, localDate, productName, late }, link) → Message`, using the M12 `Message` shape from `@pcp/notifications`:
  - subject `Daily report — <product> — <localDate>`
  - the text and HTML list every section, and missing sections say "No data: <reason>"
  - the narrative block says "Narrative deferred: the AI summary could not be verified" when deferred
  - Slack gets the summary plus a link; the webhook gets JSON with the snapshot

**Interfaces:**
- `dispatchDueReports(deps: { scheduler, queues, now }) → Promise<number>`
  - For each due row: compute `reportWindow(tz, time, row.next_run_at)`, enqueue `report-generate` (entity schedule, `window` = localDate), and call `pcp_advance_report_schedule(id, row.next_run_at, nextRunAt(tz, time, row.next_run_at))`.
  - The worker loop runs it every 60 s.
- `reportHandlers(deps: { prisma, queues, now, sources(ctx, productId), provider, appOrigin, delivery: DeliveryDeps })` returns:
  - **`'report-generate'(ctx, scheduleId, job)`:**
    1. Load the schedule. If it is gone, return `{ skipped }`.
    2. If the schedule creator has no access to the product, return `{ failed: 'not_found' }` and do nothing more.
    3. Take the version from `window`, `v1` by default. If a row already exists for `(schedule, localDate, version)`, skip to step 6.
    4. Build the snapshot and narrate. AI is disabled when `ai_settings.disabled` is set or the provider is null.
    5. Insert the report (`late` when `now − scheduled time > 15 min`) and its deliveries in one transaction. A unique violation means another run won: reload.
    6. Enqueue `report-deliver` for every delivery that is not `sent` or `dead`.
  - **`'report-deliver'(ctx, deliveryId, job)`:** `renderReport`, then `sendToChannel`, or `sendMail` for direct recipients. It records `sent`, `failed`, or `dead` (dead on the last of 5 attempts) and throws to retry.
- `createReportSources(deps: { prisma, vmQueryUrl }) → (ctx, productId) => ReportSources`
  - Database queries run through `withTenant`.
  - VictoriaMetrics instant queries at `window.end`, with `extra_label=tenant_id=<org>` and `extra_filters[]={product_id="<product>"}`, ranges `[<hours>h]`:
    - hosts: `avg_over_time` and `max_over_time` over the host metric expressions
    - log errors: `increase_pure({__name__=~"log_lines(_total)?",level="error"}[...])`
    - websites: `avg_over_time(website_up[...])`
  - Coverage:
    - `ok` when the source has data in the window
    - `partial` when data starts after `window.start`
    - `missing`, with a reason, otherwise
