# M17 Installation Methods Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Every MVP installation method from WB-05 works and is offered in the dashboard. These are the one-liner, Ansible, cloud-init, and the Docker Compose profile, plus the opt-in assisted SSH install that leaves no credential behind.

**Architecture:**
- **Fleet snippets:** the enrollment API returns the install parameters (control URL, download URL, token) beside the one-liner. The "Add server" dialog renders four tabs from them. The token stays shown-once.
- **Fleet tooling:** lives in `infrastructure/install/`. The Ansible role and cloud-init both wrap the same `install.sh`. The Compose profile runs `pcp-agentctl` in a container with host PID, host network, and `/` mounted read-only at `/hostfs`. The collector uses `root_path: /hostfs` when `PCP_HOST_ROOT` is set.
- **Installer runner:** `apps/installer-runner` is a small Go HTTP service on the internal network.
  - It holds session keys, enrollment tokens, and passwords in memory only.
  - It runs one fixed install command and one fixed cleanup command over SSH.
  - It reports host status and output to the API over the internal token.
  - The API owns `install_sessions` and `install_session_hosts`. Neither table has a column that can hold a credential.

**Tech Stack:** NestJS API, Prisma migration 0016, Go (`golang.org/x/crypto/ssh`), Next.js, Vitest, agent-e2e with systemd and sshd containers, ansible-core in a controller container.

**Spec:** spec §4.12, §8.11; master plan M17.1–M17.3; WB-05 (UC-05-02..06, BR-05-01..06, TC-05-04, TC-05-06..09).

## Global Constraints

- The platform never stores root passwords or SSH private keys after a session (BR-05-01).
- An assisted install runs only the fixed install command and the fixed cleanup command. It offers no shell (BR-05-02).
- The runner refuses to install before the admin confirms the host-key fingerprint. If the host key changes after confirmation, the host aborts (BR-05-03).
- The dashboard shows the published egress IPs (`INSTALLER_EGRESS_IPS`) (BR-05-04).
- `install_sessions` and `install_session_hosts` have no column that can hold a credential (BR-05-05).
- Limits: at most 10 hosts per session. A session expires after 1 hour, and its keys are destroyed on expiry, abort, or completion.
- Fleet token expiry is at most 24 h, as today. A cloud-init snippet needs a token that covers the provisioning window.
- Installer flags `--enable-helper` stay off by default (BR-05-08).

## Review Focus

1. **Enrollment token in output:** the token appears in the install command line. Runner output stored or shown must have the token and any password replaced by `[redacted]`.
2. **Cleanup fails** (the host is unreachable after install): the host shows `cleanup_failed` with the exact manual commands. The session still destroys its key.
3. **Unreachable host or wrong port:** the host fails with a readable reason. Other hosts in the session continue.
4. **Ansible re-run on an enrolled host:** nothing changes (`changed=0`).
5. **Password mode:** the password is never echoed into output, never logged, and never stored.

- Create: `apps/api/src/modules/install-sessions/*`:
  - `POST /environments/:id/install-sessions` (hosts, mode) creates a session with its own enrollment token: `maxUses` = number of hosts, 1 h. It asks the runner for a key and returns the public key, the setup command, and the egress IPs.
  - `POST /install-sessions/:id/connect` with `{password?}`: the runner reads each host key.
  - `POST /install-sessions/:id/hosts/:hostId/confirm-fingerprint` with `{fingerprint}`: the runner installs, then cleans up.
  - `GET /install-sessions/:id`
  - `DELETE /install-sessions/:id`: abort; the runner destroys keys.
  - `POST /internal/v1/install-sessions/:id/hosts/:hostId`: runner reports; internal token.
- Create: `apps/web/components/agents/assisted-install.tsx`. This is the wizard: hosts, then the key command and egress IPs, then "Key added", then confirm each fingerprint, then live output (polled every 2 s), then the cleanup status. Wire it as a fifth tab.

**Runner rules (from the spec):**
- Each session gets an ed25519 key pair generated in memory. The setup command for the admin is:
  `sudo useradd -m -s /bin/bash pcp-install && echo 'pcp-install ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/pcp-install && sudo install -d -m 700 -o pcp-install ~pcp-install/.ssh && echo '<pub>' | sudo tee ~pcp-install/.ssh/authorized_keys`
- **Connect:** captures the SHA256 host-key fingerprint during the handshake and authenticates. The status becomes `awaiting_confirmation`.
- **Install:** runs only if the confirmed fingerprint equals the one presented on the install connection. The command is
  `curl -fsSL <origin>/install.sh | sudo bash -s -- --token <t> --control-url <c> --download-url <d>`.
  In password mode, `sudo -S` reads the password from stdin.
- **Cleanup (key mode):** schedules `userdel -r pcp-install` and removes the sudoers file in the background, then disconnects. It verifies cleanup by reconnecting with the key, which must fail. If it does not fail, the host is marked `cleanup_failed` with the manual commands. Password mode has no user to remove; the dashboard tells the admin to rotate the password.
- Output is capped at 64 KB, with the token and password redacted before it leaves the runner.
