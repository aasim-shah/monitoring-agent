# M16 Operational Actions and Approvals Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin enables "Restart service" for production, with Owner/Admin approvers. An operator, or the AI on their behalf, proposes restarting `firemaps-api.service` on `vps-1`. Then:
1. The proposal shows a dry-run and its impact.
2. A different admin approves it.
3. The platform issues a signed 10-minute task. The opt-in root helper on the host checks it against its local allowlist and restarts the unit.
4. The unit is verified `active`, and the action is audited and added to the incident timeline.

Cloudflare cache purge and GitHub workflow dispatch go through the same engine and become usable once their connections exist (M7).

**Architecture:**
- **`packages/automation`** is the pure engine:
  - capability catalog
  - policy evaluation
  - lifecycle transitions
  - dry-run and impact (from the asset graph)
  - adapters for Cloudflare and GitHub, over an injected HTTP client
- **The api** owns requests, approvals, and executions in PostgreSQL. On approval it executes:
  - host restarts become a signed `action` agent task (the M5 task channel, with `approvalId` set)
  - provider adapters are called directly
- **The agent** forwards `action` tasks unchanged over a unix socket to `pcp-helper`. The helper is a separate root daemon, opt-in with `--enable-helper`.
  - It verifies the Ed25519 signature with a root-owned copy of the platform key, the expiry, single use, and the customer-owned allowlist `/etc/pcp-agent/helper.yaml`.
  - It runs `systemctl restart <unit>` (argv, never a shell) and waits up to 60 s for `active`.
- **The worker** expires approvals still pending after 1 h. Executions whose task outlived its 10 min TTL also expire.

**Tech Stack:** Prisma 6 and RLS, NestJS 11, Go 1.23 (`pcp-helper`, a `gopkg.in/yaml.v3`-free line parser), Ed25519 (`crypto/ed25519`, the existing canonical JSON), systemd, Next.js 15, Playwright, and agent-e2e with a systemd container.

**Spec:** spec §13.5, §18.3, Scenario B steps 7–8; inital.md §16; master plan M16.1–M16.4, D20, §3 tasks; `docs/workbooks/WB-16-operational-actions-approvals.md`.

**Deferred:**
- `host.pack_install`, M18.3 (same flow, new capability).
- Second approval for production actions beyond the first. The spec says "additional approval for production, destructive, or broad-impact": here production needs an approver other than the requester, and purge-everything needs two approvals.

## Global Constraints

- **Policies (BR-16-01):**
  - Every action policy defaults to disabled. A proposal without an enabled policy for its capability and environment is `rejected_policy` (TC-16-01).
  - Default approver roles are Owner/Admin in production and Operator and up elsewhere (WB-16 §13).
- **AI proposals (BR-16-02):** the AI only proposes (tool `proposeAction`). AI proposals always need approval, even when the policy allows none (TC-16-03), and are flagged "proposed by AI".
- **Production approval (BR-16-03):** in production the approver must differ from the requester (TC-16-02). An approver who lost the approver role or `action.approve` is refused.
- **Tasks (BR-16-04):** Ed25519-signed (the existing `TASK_SIGNING_KEY`), 10 min TTL, single use. Approval issues a new task; old tasks are never reused.
- **Host actions (BR-16-05):**
  - They need `pcp-helper` plus a unit listed in `/etc/pcp-agent/helper.yaml`, which is root-owned and edited only by the customer.
  - The helper checks the allowlist at execution time (TC-16-06).
  - The helper trusts only `/etc/pcp-agent/task-signing.pub` (root-owned, written by the installer), never the agent's state file.
- **Concurrency (BR-16-06):**
  - One action per target at a time: a second approval on a busy target waits as `approved`, and executes when the first finishes (TC-16-04).
  - Proposals carry an idempotency key. The same key returns the original request.
- **Lifetimes:** an approval still pending after 1 h becomes `expired`. A task not executed within 10 min becomes `expired`.
- **Audit (BR-16-08):** every row records initiator, target, capability, policy decision, approver, execution location, adapter version, start and end, result, and verification (TC-16-10).
- **No shell (BR-16-09):** no arbitrary shell and no AI-generated command, ever. Units match `^[A-Za-z0-9@._-]+\.service$`.
- **Limits:** Cloudflare purge takes at most 30 URLs; purge-everything needs a second approval from another approver (TC-16-08). GitHub dispatch only for an allowlisted workflow file and ref (TC-16-07).
- **Permissions:**

  | Action | Permission |
  |---|---|
  | View actions | `incident.view` (all roles) |
  | Propose | `action.propose` (operator and up) |
  | Approve or reject | `action.approve` (owner) or the policy's approver roles |
  | Manage policies | `org.settings.manage` |

## Review Focus

1. **A compromised agent account** (the `pcp-agent` user) writes its own task or swaps the signing key in `state.json`. Expected: the helper refuses, because it verifies with the root-owned key and checks single use and expiry. Task 3.
2. **A unit name with shell metacharacters** (`x.service; rm -rf /`), or a path such as `../../etc/passwd`. Expected: refused at proposal and again in the helper; `systemctl` gets argv only. Tasks 2 and 3.
3. **An approver approves their own production request** through the API, or approves after losing the role. Expected: 403 or 404, audited. Task 4.
4. **Double-click approve, or two requests on one unit.** Expected: one execution at a time and one task per approval. Task 4.
5. **The helper is missing, the agent is offline, or the unit crashes right after the restart.** Expected: `expired`, or `failed` with a reason. Never `succeeded` without verification. Tasks 3 and 4.

### Task 3: `pcp-helper` and agent forwarding

**Files:**
- `agents/host-agent-go/cmd/pcp-helper/{main.go,helper.go,allowlist.go,helper_test.go}`
- `agents/host-agent-go/internal/control` (reuse `VerifyTask`)
- `agents/host-agent-go/cmd/pcp-agentctl/main.go` (forward `action` tasks)
- `agents/host-agent-go/installer/install.sh` (`--enable-helper`)
- `agents/host-agent-go/packaging/systemd/pcp-helper.service`
- the release Dockerfile (ship the helper binary)
- the agent version, bumped to 0.3.0

**Interfaces:**
- **Socket:** `/run/pcp-helper/helper.sock`, mode 0660, owner `root:pcp-agent`. Its directory is 0750.
- **Protocol:** one JSON line in (the full signed task) and one JSON line out `{status, result?, error?}`.
- **Checks, in order:**
  1. signature, against `/etc/pcp-agent/task-signing.pub`
  2. `type == "action"`, `payload.capability == "service_restart"`
  3. not expired
  4. not used before (`/var/lib/pcp-helper/used-tasks`, entries pruned after 24 h)
  5. the unit is in the allowlist and matches the unit pattern
- **Restart:** `exec.Command("systemctl", "restart", unit)`, then up to 60 s polling `systemctl is-active <unit>` for `active`. The result is `{unit, restarted: true, activeState}`.
- **Agent:** agent 0.3.0 forwards `action` tasks to the socket, with a 90 s timeout. With no socket it fails with "pcp-helper is not installed on this host (re-run the installer with --enable-helper)".
- **Installer:** `--enable-helper` installs the binary and the unit, copies the task key from the enrollment response to `/etc/pcp-agent/task-signing.pub` (0644 root), and creates `/etc/pcp-agent/helper.yaml` (0644 root) with an empty allowlist if absent. It never overwrites the allowlist.

- [ ] Failing Go tests (the systemctl runner is injected):
  - a valid task restarts and verifies
  - TC-16-05: an unsigned, tampered, or expired task, or a replayed ID, is refused
  - TC-16-06: a unit not on the allowlist is refused
  - a unit with metacharacters is refused
  - a signature made with a key swapped into the agent state is refused (Review Focus #1)
  - TC-16-09: a unit that is not `active` within the window gives `failed` "unit is failed after restart"
  - the socket mode is 0660 with group `pcp-agent`

  Implement, pass (`scripts/go.sh test ./...`), commit.

**Execution (`executor.ts`):** on `approved`:
1. Take the target slot (the unique running `target_key`). If it is busy, leave the request `approved` and retry when the running execution finishes.
2. Host: create an `action` agent task (TTL 600 s, `approvalId` = the approval ID, resource scope `{agentId, unit}`).
3. When the task result arrives (a TasksService result handler): verification is the helper's `activeState == active`. The execution and request become `succeeded` or `failed`. Audit `action.execute`, add an incident timeline event "Action …" when `incident_id` is set, and notify the requester by email when channels exist.
4. Provider capabilities without a connection are refused at proposal with `connection_required`.

- **Sweep:** each alert tick expires requests pending for more than 1 h, and executions whose task expired without a result.
- **AI tool `proposeAction`:** creates a proposal with `proposed_by_ai`, which always stays `pending_approval`. It never approves or executes.
