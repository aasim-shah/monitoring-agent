# M13a Website Monitoring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin adds `https://shop.example.com` to a product and proves control of the domain with a DNS TXT record. From then on the platform probes the site every minute and records:
- status
- redirects
- latency and TTFB
- TLS expiry

The site is down after 2 consecutive failed probes, and a certificate expiring within 14 days raises a warning. Both open incidents through the M12 engine. The AI assistant can answer "Is the shop up?" with evidence.

**Architecture:**
- **Monitors** live in a tenant table, `website_monitors`.
- **The worker runs one scheduled job per monitor** (`website-probe`, every `interval_seconds`):
  1. If the domain is not verified, it checks the DNS TXT record `pcp-verify=<token>` (on the host or a parent domain) and does not probe.
  2. Otherwise it probes through the SSRF-guarded HTTP client, measures TLS with a separate TLS handshake, stores the last result on the monitor, and imports `website_*` samples into VictoriaMetrics with `tenant_id`, `product_id`, and `monitor_id` labels.
- **Alert rules** `website_down` and `website_tls_expiring` are worker-evaluated templates in the existing per-tenant alert tick.
- **The web** gets the Websites & APIs page. The AI tool `getWebsiteAvailability` reads the monitors and their last results.

**Tech Stack:** Prisma 6 and RLS, BullMQ, undici (SSRF-pinned), `node:tls`, `node:dns/promises` `resolveTxt`, the VictoriaMetrics import API, NestJS 11, Next.js 15, Playwright.

**Spec:** spec §6.2, §7.4; master plan M13.5, D23, §3 (default probe interval 60 s, minimum 30 s; TLS warning at 14 days); WB-09 UC-09-01..03, BR-09-01/02/06, TC-09-01..03.

**Deferred:**
- KPI definitions and freshness (M13.6) move to M13b with GA4, where KPIs come from.
- Cloudflare-zone verification waits for the Cloudflare connector (M7/M4 scope).
- Private URLs through the agent `http-check` pack, and multi-region probes.

## Global Constraints

- **Verification before probing.** An external site is probed only after domain verification (BR-09-01, TC-09-01).
  - **What counts:** the TXT value `pcp-verify=<token>` is found on the URL's host or on a parent domain, never on a bare public suffix.
  - **Unverified monitors:** checked every minute for 24 h, then paused with the reason "verification timed out".
  - **Re-verification:** every 30 days. If it fails, probes pause with a notice.
- **Intervals.** The default is 60 s and the minimum 30 s. Each organization has at most 50 monitors.
- **Probe.** SSRF-guarded (`assertPublicDestination` with a pinned address), 10 s timeout, at most 10 redirects (a loop is reported), and the body read capped at 64 KB.
  - **Recorded:** status code, final URL, redirect count, total time, TTFB, TLS expiry and issuer, and `challenge` when a Cloudflare challenge page is detected.
  - **Up** means the expected status (default: any 2xx or 3xx after redirects) and no network or TLS error.
- **Never zeros for missing data.** A probe that did not run (paused or delayed) writes nothing to VictoriaMetrics. A delayed probe never marks a site down.
- **Alerts:**
  - `website_down` fires after 2 consecutive failures (critical).
  - `website_tls_expiring` fires when the certificate expires in under 14 days (warning).
  - Both resolve when the condition clears.
- **Permissions.**

  | Action | Permission |
  |---|---|
  | View monitors | `telemetry.query` |
  | Create, delete, re-check | `pack.manage` (operator and up) |

## Review Focus

1. **A monitor URL pointing at `http://169.254.169.254/`, `https://10.0.0.5`, or a host whose DNS resolves to a private address.** Expected: creation is refused, and a later DNS change to a private address is refused at probe time. Tasks 2 and 4.
2. **A TXT record on `com`, or the token on an unrelated domain.** Expected: not verified, and nothing is probed. Task 2.
3. **A redirect loop, or a redirect to a private address.** Expected: the loop is reported after 10 hops, and the private hop is blocked. Task 2.
4. **A site that is down for one probe only.** Expected: no incident. Two failures open one, and a recovery resolves it. Task 3.
5. **Another tenant's monitor ID** in the API or the AI tool. Expected: 404 or not found. Tasks 4 and 5.

### Task 2: Probe and domain verification (`packages/website-probe`)

**Interfaces:**

- `probe(url, { timeoutMs, maxRedirects, destination, expectedStatus, now }) → ProbeResult`, where `ProbeResult` is `{ up, statusCode, finalUrl, redirects, totalMs, ttfbMs, tls: {expiresAt, issuer} | null, error?, challenge? }`.
- `verifyDomain(host, token, resolveTxt) → { verified, checkedNames[] }`. It walks from the host up to the registrable domain and never checks a single-label TLD or a known public suffix (a small built-in list such as `co.uk` and `com.pk`).

### Task 3: Worker job and alert templates

**Behavior:**
- **`website-probe` handler:**
  1. A pending monitor runs `verifyDomain`; after 24 h it pauses.
  2. An active monitor is probed, the row is updated (`consecutive_failures` is incremented or reset), and samples go to `VM_IMPORT_URL/api/v1/import/prometheus`: `website_up`, `website_response_seconds`, `website_ttfb_seconds`, `website_status_code`, `website_redirects`, and `website_tls_expiry_days`.
  3. Monitors are re-verified every 30 days.
- **Templates** `website_down` (2 failures, critical) and `website_tls_expiring` (`days`, default 14, warning) have kind `website`. The alert tick evaluates them from the monitor rows, with labels `{monitor_id, url}`. Both are added to `RECOMMENDED`.
- **Worker config:** `VM_IMPORT_URL`.

### Task 4: API

**Routes:**
- `GET/POST /api/v1/products/:id/website-monitors` takes `{url, intervalSeconds?, expectedStatus?}`.
  - The URL must be https or http, with a public host checked at creation through the DNS resolver.
  - The response includes `verification: { record: 'TXT', name: <host>, value: 'pcp-verify=<token>' }`.
  - Creation upserts the job definition `website-probe` for the monitor (every interval).
- `DELETE /api/v1/website-monitors/:id`.
- `POST /api/v1/website-monitors/:id/verify` checks now.
- **The AI tool `getWebsiteAvailability`** returns the monitors with their last result and uptime over the window (`avg_over_time(website_up[range])`).
